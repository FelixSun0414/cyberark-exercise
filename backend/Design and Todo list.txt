Current solution:
- save the mappings into the database
- use Affine Permutation to generate unique code from unique integer id retrieved from database
- short code is saved in the database table, but actually it's not essential for small system since the code could be reversed back to the id and query with id.
    - reversing could be done in service and takes O(1) time complexity, so database will be off-loaded a little bit on storage and query
    - without saving the short code, it means the algorithm and Affine_A/Affine_B constants can never be changed
    - without saving the short code, we will lose the benefit of CDN because every GET request has to come to the service to get reversed to the id
- return 200 for existing records
    - does not allow re-shortening the same URL, since there could be a lot of resource wasted.
- make the status_code configurable for redirection

Back of the envelope est:
1. Assume 1000 POST requests per second, and 1000 x 10 GET requests per second.
    - MySQL server is able to handle this, especially url shortener service is a read heavy service, LRU + Redis cache will greatly lower the service load.
    - CDN or any edge service could also be used to off-load the service.

2. For constant 1000 POST QPS, assume the service will run for 20 years, there will be 1000 * 60 * 60 * 24 * 365 * 20 = 630,720,000,000 records, less than 62^7 = 3,521,614,606,208
    - the current implementation allows up to 62^8 records, it has a lot of room for wasting Ids

3. Network:
    - every POST request will carry a 250 chars URL, with additional 250 chars headers. the response also carries the original URL and new code and additional headers, consider to be 700 chars.
    - every GET request use short URL which could be ignored, only consider additional 250 chars headers. the response return the average 250 length original URL, and additional 250 chars payload.
    - in total, the minimum network bandwidth will be: (250 + 250 + 700) * 1000 + (250 + 250 + 250) * 10000 = ~ 69.6 Mbps
    - considering additional overhead costs (x 1.5) and peak request costs (x 2), suggested network bandwidth: 70 Mbps * 1.5 * 2 = 210 Mbps

4. Storage: every record may need 250 bytes for URL, and additional 100 bytes (code, indexing etc.). so
    - for 10 years, storage: (250 + 100) * 1000 * 60 * 60 * 24 * 365 * 10 = ~100TB
    - for 20 years, storage: ~100TB * 2 = ~200TB
    - Note: the storage will vary based on the average URL length
